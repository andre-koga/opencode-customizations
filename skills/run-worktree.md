# Run worktree

Use this workflow when the user invokes `@run-worktree`. Run the frontend in the **current session's existing Git worktree**, without pushing or deploying. This is a preview request, not permission to change application code or create a new worktree. Follow all applicable worktree and security instructions. Do not run commands that write inside an original checkout: if the current session is there, explain that the user should invoke this skill in the worktree they want to preview and stop. Never switch branches, change other worktrees, kill unrelated processes, or print secrets, session tokens, or environment-file contents.

1. Identify the current repository root, branch, and worktree, and check its frontend's own instructions and scripts. Locate the frontend package (for example, `apps/web` in a monorepo). If the frontend cannot be identified, ask instead of guessing. Use the current worktree's files, including uncommitted changes, rather than a different checkout. Confirm it is a dedicated task worktree and branch before running anything that writes files.
2. Check prerequisites and the worktree's frontend environment without displaying secret values. Authentication configuration and API endpoints must belong to the same environment; inspect the project's documented requirements and environment example. Never silently copy another checkout's environment file, overwrite an existing one, or fall back to production. If configuration is missing or mismatched, explain the exact variable names and ask the user how to configure it. Do not claim login works just because the server starts. Warn that interactions use the configured real backend and can change its data.
3. Reuse an already-running preview only after verifying it belongs to this exact worktree and is healthy. Otherwise choose an available loopback port, preferring a deterministic port for this worktree so the same origin can be reused on later runs. If occupied, choose another free port and report that signing in again may be necessary. Do not stop the process occupying it. Use `localhost` consistently (not `127.0.0.1` in the browser URL) and bind only to loopback. For Vite, avoid races with `--strictPort`; if the chosen port becomes occupied, select another and retry. Never mistake an unrelated server's response for this preview.
4. Start the frontend in the background using the worktree's documented workflow. Build and watch shared workspace packages when the frontend consumes their built output; do not launch Vite alone if the documented runner also watches a UI package. Use the existing runner if it safely supports a chosen port, otherwise use the equivalent documented build/watch workflow. For Vite, use `--host 127.0.0.1 --port <port> --strictPort`. Check actual scripts and CLI syntax first. Install dependencies only if needed, using the worktree's documented package manager and lockfile; do not change tracked files or other worktrees. Leave successful preview processes running, and report useful process/job identifiers and how to stop just these processes. If startup fails, diagnose and report the failure instead of claiming success.
5. Verify the server responds and open `http://localhost:<port>/` in the OpenCode desktop side-panel browser. Load the browser skill first and use the built-in `browser` tools, not an external browser. Inspect the page and console for obvious startup errors. If the desktop browser is disconnected, report that and provide the URL instead; do not retry a disconnected browser or claim it opened. Keep the browser tab open for the user.
6. Ask the user to sign in in the side panel if needed; never enter credentials, copy cookies or tokens from another origin, or bypass browser security. Browser session storage is scoped to scheme, hostname, and port, so a deployed app's login is separate from localhost and a different port may require another login. Reusing the same browser profile and URL can preserve the local login, subject to the app's authentication design, browser persistence and session expiry. Do not guarantee persistence across app restarts without testing it. Report the URL, worktree, branch, backend environment, any startup errors and authentication limitations concisely.
